## 돌리는 법

```bash
docker compose up            # 또는 npm install && npm start
# 브라우저에서 http://localhost:9376

npm test                     # 178개, 약 19초 (통합 테스트가 실제 소켓을 씀)
```

런타임 의존성은 `express` 하나뿐이고 빌드 단계가 없습니다. 차트 라이브러리(uPlot)는 `public/vendor/`에 커밋돼 있어 오프라인에서도 돕니다. Node 20 이상.

## 먼저 알아야 안 헷갈리는 세 가지

### 1. 배포 구간은 빈칸이 아니라 빨간 구간으로 보입니다

> 오해하면: 정상 동작을 고장으로 읽습니다.

레코드의 시각이 **발사 시각**이고 스케줄러는 대상이 죽어도 계속 쏘기 때문에, 끊긴 초에도 버킷이 생깁니다 — 그 안이 전부 실패일 뿐입니다. 성공선이 0으로 떨어지고 실패가 빨갛게 차오르는 모습이 실제로 보게 될 그림입니다.

챌린저에게 "그래프에서 공백을 찾으세요"라고 안내하면 정상 동작을 고장으로 오해합니다. 문서는 이미 고쳐놨습니다.

### 2. 대상은 반드시 랩과 별도 프로세스여야 합니다

> 오해하면: 아무것도 관측되지 않습니다.

프로버와 실행 저장소가 랩 프로세스 안에 들어 있습니다. 그래서 랩 자신을 재시작하면 측정 엔진까지 같이 죽어, 순단이 아니라 측정 자체가 사라집니다. 실습 안내문에 이 문장을 꼭 넣으세요.

### 3. 베이스라인 창이 지난 다음에 배포해야 합니다

> 오해하면: 도구가 오진을 냅니다.

측정 시작 후 첫 **30초**(기본값)가 "평상시" 기준입니다. 배포가 그 안에서 일어나면 끊긴 구간이 기준값에 섞여 들어가, 델타가 정상으로 읽히고 도구가 *"배포 전부터 실패가 있었습니다"*라고 엉뚱한 진단을 내놓습니다. README 3단계에 적어뒀습니다.

## 실제로 측정해 확인한 값

컨테이너에서 별도 대상 서버를 4초간 강제 종료 · 10 rps

| 항목 | 값 |
|---|---|
| 감지된 순단 | 1회 · 4199ms |
| 실패 건수 | 41건 (이론값 42 = 10rps × 4.2초) |
| 실패 분류 | 전부 `network` |
| 실패율 / 평소 | 20.5% / 0.0% |
| 보내지 못한 요청 | 0건 |

호스트에서 직접 돌린 결과도 4200ms / 41건으로 사실상 동일했습니다. 순단 지속시간은 **직전 성공부터 다음 성공까지**를 재므로, 사용자가 체감하는 단절과 같은 정의입니다.

## 인수 후 추가된 변경과 그에 따른 주의

인수인계 시점(`eb448fe`) 이후 커밋 4개가 들어왔습니다.

- 2주차 워크북 자료(Alloy 설정 + Grafana 대시보드)가 `workbook-assets/`에 추가
- 앱 스크레이프에 `instance` 라벨 추가 — 2대가 같은 시계열에 쓰던 문제 수정
- 실패가 전부 `server`로 나올 때 시나리오부터 의심하라는 절 추가
- **rps 상한이 200에서 1000으로 상향**

마지막 변경은 확인해 볼 지점이 있어 직접 돌려봤습니다.

같은 대상 · 12초 측정

| 설정 | 발사 | 미발사 |
|---|---|---|
| rps 200 (이전 상한) | 2,399 | 1건 |
| **rps 1000 (현재 상한)** | 10,419 | **1,582건 (13%)** |

rps 1000으로 돌리면 슬롯의 13%가 아예 나가지 못하고, 도구가 스스로 *"보내지 못한 요청이 있습니다 — 이 실행의 수치는 신뢰할 수 없습니다"* 경고를 띄웁니다. 상한은 올라갔지만 그 근처에서는 실질적으로 쓸 수 없는 상태입니다.

원인은 요약을 5초마다 만들 때 그동안의 응답시간 배열을 전부 정렬하는 비용이 스케줄러와 같은 이벤트 루프를 막는 것입니다. 최종 리뷰가 "극단 설정에서 일어날 수 있다"고 짚었던 건인데, 상한이 올라가면서 기본 지속시간(300초)에서도 닿게 됐습니다.

덧붙여 두 가지:

- 경고 판정이 `미발사 > 0`이라 **rps 200에서도 12초에 1건만 놓쳐도 같은 배너가 뜹니다** (2,399건 중 1건, 0.04%). 13%와 0.04%가 같은 경고를 받는 셈이라 임계값을 두는 편이 낫습니다.
- 순단 중복 제거 키로 **시작 시각**을 쓰는데, rps 200에서는 발사 간격이 최소 5ms라 두 성공이 같은 밀리초를 가질 수 없어 안전했습니다. rps 1000에서는 간격이 1ms이고, 실제로 348번 발사 중 8쌍이 같은 밀리초를 공유했습니다. 다만 두 순단 사이에는 최소 연속 실패 수만큼의 간격이 끼므로 당장 터지는 문제는 아닙니다 — 상한을 더 올리거나 최소 연속 실패 수를 1로 내릴 때 재검토가 필요합니다.

## 의도적으로 넣지 않은 것

아래 네 가지는 빠뜨린 게 아니라 범위에서 뺀 것입니다. 실제로 코드에 없는지 대조했습니다.

| 항목 | 이유 |
|---|---|
| 배포 트리거 | 배포는 챌린저가 자기 방식대로 합니다. 이 도구는 관측만 합니다 — GitHub Actions든 ArgoCD든 수동 SSH든 가리지 않습니다. |
| 테스트 데이터 정리 | 앱마다 방식이 너무 달라 랩이 관여할 영역이 아닙니다. 측정 중 대상 앱에 진짜 계정이 쌓이고, 바디 기본값의 `lab-` 접두어가 나중에 지울 때의 기준입니다. |
| Prometheus / Grafana | 15초 스크랩 격자로는 수 초짜리 순단이 점 하나로 뭉개집니다. 관측 챕터에서 직접 붙여보는 것이 그 챕터의 실습 내용이고, 그 자료가 지금 `workbook-assets/`에 들어왔습니다. |
| 램프업 부하테스트 | 측정 목적이 다릅니다. 유실 측정은 꾸준한 저빈도 탐침이 필요하고, 한계점 탐색은 계단식 증가가 필요합니다. |

**부하테스트 챕터와의 연결고리.** 화면의 "k6 스크립트 내려받기"가 폼에 맞춰둔 규격(주소·헤더·바디·성공 판정)을 그대로 k6 스크립트로 뽑아줍니다. 챌린저가 API 규격을 두 번 맞추지 않아도 됩니다.

## 남은 것

### 확인 권장 — 측정값에 영향

**rps 상한 1000의 실효성.** 위에서 측정한 13% 미발사. 상한을 되돌리거나, 요약 계산을 런닝 집계로 바꾸거나, 미발사 경고에 임계값을 두는 세 방향이 있습니다.

### 테스트 공백

**새로고침 복구와 차트 배선.** 측정 중 새로고침하면 진행 중인 실행에 다시 붙는 기능은 DOM 테스트 하니스가 없어 자동 테스트가 없습니다. `public/chart.js`의 uPlot 설정(`spanGaps:false` 등)도 같은 이유로 테스트가 없어, 나중에 누가 지워도 `npm test`는 통과합니다.

### 표시 문제 — 데이터는 정확

**중지 직후 피드백.** 중지를 누르면 진행 중이던 요청이 정리될 때까지 최대 타임아웃 시간(기본 5초) 동안 폼이 잠기는데 "중지 중" 표시가 없습니다. `POST /stop`이 아직 `{status:"running"}`을 반환하는 것도 같은 이유입니다.

**베이스라인 전에 중지한 경우.** 베이스라인 창이 차기 전에 중지하면 완료된 실행에도 "평소 측정 중"이 남아, 아직 측정 중인 것처럼 읽힙니다.

## 어디를 읽어야 하나

**설계 근거는 `docs/superpowers/specs/2026-09-13-zero-downtime-lab-design.md`** 에 있습니다. 특히 4장(측정 설계)이 왜 이렇게 만들었는지를 담고 있어서, 워크북 본문 쓸 때 그대로 쓸 만합니다 — 응답을 기다리고 다음 요청을 보내면 안 되는 이유, 타임아웃을 백분위수에 섞으면 안 되는 이유, 순단을 성공과 성공 사이로 재는 이유가 각각 한 절씩 있습니다.

코드는 측정 단계별로 나뉘어 있습니다.

```
src/prober/      발사와 분류 — scheduler, classify, sequence-buffer
src/analysis/    집계 — bucketer, outage-detector, baseline, percentiles
src/run/         실행 오케스트레이션
src/api/         REST + SSE + 시나리오 검증
src/export/      k6 스크립트 생성
public/lib/      브라우저와 Node 테스트가 공유하는 순수 로직
```

`src/prober/sequence-buffer.js`는 왜 있는지 모르면 지우고 싶어지는 모듈입니다. 요청은 발사 순서대로 나가지만 완료 순서는 뒤집히고(타임아웃된 요청이 나중에 발사된 성공보다 늦게 끝납니다), 그 순서 그대로 순단 감지에 넣으면 연속 실패 구간이 성공으로 잘려 순단이 아예 안 잡힙니다. `test/integration.test.js`의 세 번째 테스트가 그 경로를 실제로 강제하고, 왜 두 조건이 함께여야 하는지 주석에 남겨놨습니다.
